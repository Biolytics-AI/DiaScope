This example is designed for healthcare buyers, legal reviewers, compliance stakeholders, and information security teams. It uses DiaScope to walk through a blueprint for compliant GPU-backed AI processing when clinical context leaves a healthcare provider's current hosting environment.

It is intentionally not a deep engineering tutorial. The story starts at the outbound boundary where externally hosted processing begins, then works outward into responsibility split, provider prerequisites, rented-GPU safeguards, and reviewable evidence.

## Why this example exists

A healthcare provider wants to use AI for administrative support around EHR workflows. That means clinical context may need to reach infrastructure outside its current hosting environment.

This introduces three parties with different responsibilities:

- The healthcare provider as the controller of the EHR context and use case
- Biolytics AI as the implementation partner operating the external processing layer
- The GPU host as the infrastructure provider or sub-processor

The example uses the rented-GPU / self-managed deployment model as the reference blueprint, because it makes the required safeguards explicit. Managed inference offerings remain possible, but in those cases more trust must be established through provider evidence, certifications, contractual controls, and claims such as statelessness.

## What the walkthrough covers

1. Where provider-controlled context leaves the current hosting boundary.
2. Which controller-side decisions and identities must be in place before that handoff.
3. How responsibilities split between controller, implementation partner, and GPU provider.
4. Which legal and evidence prerequisites must exist before a provider can be onboarded.
5. Why the rented-GPU model serves as the compliance blueprint for external AI processing.
6. What evidence must remain reviewable after the response comes back.
